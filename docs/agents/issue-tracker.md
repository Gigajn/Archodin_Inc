# Issue tracker: Local Markdown

Issues and specs for this repo live as markdown files in `.scratch/`.

## Conventions

- One feature per directory: `.scratch/<feature-slug>/`
- The spec is `.scratch/<feature-slug>/spec.md`
- Implementation issues are one file per ticket at `.scratch/<feature-slug>/issues/<NN>-<slug>.md`, numbered from `01`, never a single combined tickets file
- Triage state is recorded as a `Status:` line near the top of each issue file (see `triage-labels.md` for the role strings)
- Comments and conversation history append to the bottom of the file under a `## Comments` heading

## When a skill says "publish to the issue tracker"

Create a new file under `.scratch/<feature-slug>/` (creating the directory if needed).

## When a skill says "fetch the relevant ticket"

Read the file at the referenced path. The user will normally pass the path or the issue number directly.

## Execution eligibility and legacy revalidation

For implementation work, a frontier candidate must be unblocked and explicitly ready for an agent. Triage, information requests and human-only work are not authorization to implement, even if the frontier script lists them.

Open tickets under `.scratch/aahc/issues/` require revalidation against the accepted Archodin/Basileia boundary and current product scope before implementation resumes. Preserve their existing content, completion history and user edits. Classify each open ticket as still relevant, needs revision or deferred, and obtain owner confirmation before continuing it; an old `ready-for-agent` status alone is insufficient. Record the review and confirmation in that ticket's `## Comments`.

`python3 scripts/frontier.py` offers only unblocked `ready-for-agent` tickets. `--json` returns the same eligibility with machine-readable reasons; `--all` also explains blocked and ineligible open work. `in-progress`, triage, information requests and human-only work are not new assignments. No bulk status changes or legacy execution are authorized by roadmap approval.

### Dependency syntax

Use one metadata field before the first `##` heading: `**Blocked by:** None`, local comma-separated numbers such as `01, 02`, or qualified references such as `archodin-compatibility-spike#05, basileia-roadmap#01`. An optional final sentence period and one trailing parenthesized explanatory note are allowed; numbers inside that note are not blockers. Unsupported expressions, duplicate fields/identities, missing targets and dependency cycles fail closed. Only `done` satisfies a prerequisite; `wontfix` or cancellation does not deliver its capability. A done marker does not hide a structurally invalid prerequisite graph.

### Recording legacy revalidation

After actual owner confirmation, keep one current `### Legacy revalidation` record under `## Comments`, with a nonempty `**Review:**` describing the classification/evidence and exactly one `**Owner confirmation:** approved` field. Missing, empty or conflicting review/confirmation is not approval; a marker in metadata alone is insufficient. Record the real decision, not a claim generated by the agent to unblock itself. The CLI checks the recorded convention, not cryptographic proof of human identity. Preserve older context under differently named history headings rather than leaving conflicting current decisions.

## Wayfinding operations

Used by `/wayfinder`. The **map** is a file with one **child** file per ticket.

- **Map**: `.scratch/<effort>/map.md` (the Notes / Decisions-so-far / Fog body).
- **Child ticket**: `.scratch/<effort>/issues/NN-<slug>.md`, numbered from `01`, with the question in the body. A `Type:` line records the ticket type (`research`/`prototype`/`grilling`/`task`); a `Status:` line records `claimed`/`resolved`.
- **Blocking**: a `Blocked by: NN, NN` line near the top. A ticket is unblocked when every file it lists is `resolved`.
- **Frontier**: scan `.scratch/<effort>/issues/` for files that are open, unblocked, and unclaimed; first by number wins.
- **Claim**: set `Status: claimed` and save before any work.
- **Resolve**: append the answer under an `## Answer` heading, set `Status: resolved`, then append a context pointer (gist + link) to the map's Decisions-so-far in `map.md`.
