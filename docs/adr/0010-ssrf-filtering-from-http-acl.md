# SSRF filtering at the resolver comes from http-acl; http_guard stays the policy

Resolver-level SSRF filtering comes from the `http-acl` + `http-acl-reqwest` crates (v0.14.0, Apache-2.0), wired into the one shared egress client. `http_guard` does **not** go away: it remains the single source of truth for egress policy — the values (timeout 30 s, body cap 2 MiB, redirect max 5, same-origin) and the URL-literal checks (`validate_url`, `validate_endpoint`, `same_origin`) all stay in Archodin. http-acl is the mechanism that enforces the IP part at resolve time; it is configured from `http_guard`'s values, never the other way round.

The wiring is a single constructor, `http_guard::shared_client()`, and no other place in the codebase may build an egress client. That constructor wires all three http-acl pieces together — the `HttpAcl` middleware, `.dns_resolver(middleware.dns_resolver())`, and `.redirect(middleware.redirect_policy_with_max(5))` — plus `.timeout(30s)` and `.no_proxy()`. Forgetting any one piece silently drops protection (the crate's own README warns the ACL is not enforced on resolved IPs if the DNS resolver is not set), which is why the wiring lives in exactly one place and is covered by a test that requests a blocked IP through the shared client and expects failure. Body cap and timeout stay in Archodin code (`read_capped`, 2 MiB; 30 s) because http-acl provides neither.

## Why this crate, and the hard questions

- **Filter-at-resolver is not "pinning" — does it actually close DNS rebinding?** Yes, in the standard reqwest path, and this was the most contested point of the review. The crate has no custom connector and never dials an IP itself; it filters inside `Resolve::resolve()`. That still closes the classic TOCTOU because reqwest dials exactly the `SocketAddr` the resolver returns — there is no second lookup between validation and connection (verified against hyper-util 0.1.12, the version reqwest 0.13 pins, and reqwest 0.13.0's `Resolve` trait docs). What does not exist is pinning *across* requests: each request re-resolves, but each re-resolution is filtered again, so a DNS answer that flips to a private IP is dropped on that attempt too.
- **But the protection then depends on reqwest/hyper behaviour, not on the crate. What if that changes?** The dependence is real and is recorded here. Mitigations: reqwest is pinned to 0.13 at the workspace; a rebinding regression test (stub resolver whose answer flips, in the style of http-acl's own `FixedResolver` tests) guards the behaviour; and `http_guard`'s URL-literal checks stay in front as defence in depth.
- **Why http-acl and not reqwest-ssrf-guard?** Both close the same TOCTOU hole the same way (filter in `Resolve`). http-acl wins on maturity and breadth: v0.14.0, actively maintained (three releases in three weeks, 2026-08–10), a richer ACL (host wildcard, path, header, classified denial reasons), and it already ships the IPv6-embedded fix (`::7f00:1`, `64:ff9b::/96`) that Archodin patched by hand in Fase B. reqwest-ssrf-guard is v0.2.0, one maintainer, no substantive change since 2026-09-28, no `SECURITY.md`, no fuzzing (ADR 0011).
- **What if http-acl's redirect policy cannot express same-origin?** Open verification point for the implementation: if it cannot, Archodin keeps its own redirect policy on the shared client and uses http-acl only for the DNS resolver. The fallback is defined before the code is written, not discovered after.
- **What about proxies?** http-acl says nothing about proxies, and a proxied request's target is resolved by the proxy, not by the resolver — so the IP rules would silently not apply. Archodin does not use a proxy today, and the shared client sets `.no_proxy()`; if a proxy is ever introduced, the guard must be re-verified first.

## Considered Options

- **Keep `http_guard` purely hand-rolled**: zero new dependencies, but the DNS-rebinding hole stays open (validation happens on the URL string, then reqwest re-resolves with its default resolver) and every IP-range edge case stays hand-maintained.
- **Adopt reqwest-ssrf-guard instead**: same mechanism, smaller crate, but a single maintainer, quiet since 2026-09-28, and a four-piece installation (configure + middleware + `.no_proxy()` + `.https_only(true)`) where forgetting one piece silently drops protection (ADR 0011).
- **Port fetchkit's `DnsPolicy` (transport-level pinning)**: the strongest guarantee (it pins with `resolve_to_addrs` at the transport), but it would mean owning ~600 lines of guard code plus a second egress policy, when http-acl already covers the hole and is maintained (ADR 0012).
